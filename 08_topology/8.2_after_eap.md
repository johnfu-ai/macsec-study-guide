## 8.2 EAP 鉴权成功之后

同样是两台设备，鉴权方式一换，拓扑里的角色关系就变了：不再是"两个平权的 PSK 对等体"，而是"认证者—申请者"的主从结构。这一节看 EAP 成功之后的拓扑差异——它解释了为什么 EAP 故事线里 Key Server 永远是 Authenticator。

### 8.2.1 拓扑图

```
  Authenticator (Key Server)          Supplicant
  MAC 02:00:00:00:00:0a               MAC 02:00:00:00:00:0b
  KS priority 0                       KS priority 255
           \                             /
            \   EAP-Success (unicast)
             \  then MKA to 01:80:c2:00:00:03
              +---------- LAN ----------+
```

图 8-2：EAP 鉴权成功之后的拓扑

### 8.2.2 角色变化

Authenticator 的 KS 优先级是 0、Supplicant 是 255——两端在设计上就"锁死"了选举结果：**认证者永远当 Key Server**。这与 PSK 故事线里"优先级竞争"形成对照：PSK 是协商出来的秩序，EAP 是鉴权带来的秩序。

### 8.2.3 密钥来源变化

CAK/CKN 不再来自配置，而是从 EAP 的 MSK 派生（公式见 [2.3 KDF 公式与标签](../02_key_hierarchy/2.3_kdf.md)；演示值在 [`captures/keys.json`](../captures/keys.json) 的 `eap` 条目）。值得注意的是，EAP-Success 之后的 MKPDU 使用的参数集与 PSK 握手**完全相同**——拓扑与角色变了，协议没变。完整 EAP-TLS 过程在 [ieee-802.1x-study-guide](https://github.com/johnfu-ai/ieee-802.1x-study-guide)，本仓库的 [`captures/mka-after-eap.pcap`](../captures/mka-after-eap.pcap) 从 EAP-Success 起步，逐帧解析见 [5.5 PSK 与 EAP 鉴权之后的 MKA](../05_wire_format/5.5_psk_vs_eap.md) 与字段报告 [`captures/decoded/11-mka-after-eap.md`](../captures/decoded/11-mka-after-eap.md)。
